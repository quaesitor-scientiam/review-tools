**Phase R testing lesson (TLS handshake-flood repro — 3 false guards before it caught the bug):**
Building this regression test took THREE failed attempts that all PASSED on the buggy code
(false guards). Root causes, each only found by forcing the assert to fail and printing the real
close time + instrumenting the accept loop:
1. **Bare silent `dial_tcp` doesn't stall the handshake** — mbedtls fails the empty/EOF read FAST
   (fd reuse in the trace proved workers were draining, not blocking). Need a *valid* ClientHello
   so the server accepts it and then blocks in `wait_for_read` for the client's next flight.
   Captured a real 165-byte ClientHello from V's own mbedtls client and replayed it.
2. **`tls_accept_timeouts` derives the handshake budget from `accept_timeout` when finite** — so
   `accept_timeout: 100ms` capped each stuck handshake to 100ms (NOT the `tls_handshake_timeout`
   fallback, which only applies when `accept_timeout` is 0/infinite). Workers freed in 100ms → no
   wedge. Fix: set `accept_timeout: 8s` so the budget is large.
3. **Timing/backlog** — dialing with gaps + closing too soon left the extra conns in the TCP
   backlog un-accepted, so the accept thread was polling (not blocked on the send). Dial all conns
   up front, then sleep so the accept thread fills worker+buffer and parks on the send.
Meta-lesson: a shutdown/liveness test that PASSES on the known-buggy commit is a FALSE GUARD —
Phase R ("reproduce on the buggy commit, exit 1") is the only thing that catches it. Always
force the assert to fail once to read the real measured value before trusting a timing assertion.
